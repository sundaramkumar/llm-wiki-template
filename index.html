LLM wiki template

A developer wiki that Claude Code writes from your code and keeps up to date. It works with any language or framework, for a codebase you already have or one you're just starting. This page explains how to set it up.

See the result firstExample wiki → "Acme Shop", a made-up project with four repos in four stacks: the home page, guide, system map, risk register and graph. Code already existsExisting project → Document a codebase that's live or in development, including legacy code. Little or no code yetNew project → Start the wiki with the code, and let it grow with each feature.

What you get

For each project, a separate private git repo (the "wiki repo") next to the code repos, containing:

PartWhat it is
Wiki pages (wiki/)Markdown pages on flows, modules, architecture, decisions and incidents. Every claim cites the code as repo:path → symbol.
System mapOne diagram of the whole system, plus a numbered sequence diagram at the top of each main flow page.
Risk registerEvery possible bug Claude noticed while reading the code, rated by severity, filterable and exportable to CSV.
Freshness trackingEach page records which commit it was checked against. A script lists the pages that new commits affect.
A small site (site/)A home page, a guide for your developers, the system map, the risk register and a page graph. Plain HTML, no server.
Slash commands/wiki-init, /wiki-build, /wiki-sync, /wiki-ask, /wiki-lint in Claude Code.

The wiki explains what the code can't say on its own: paths that cross files and repos, why things are built that way, business rules and gotchas. The code stays the source of truth.

Steps for a new project ↓

Both need: git, Node.js 18+ (for the scripts, whatever your project's language), and Claude Code.

Existing project

  1. Put the repos side by side. Clone every repo of the project into one folder and check out the branch the team works on (often main or dev). 
    ~/Projects/Acme/
├── acme-api/
├── acme-web/
└── acme-mobile/
  2. Copy the template next to them as <project>-wiki: 
    cp -R ~/Projects/Personal/llm-wiki-template ~/Projects/Acme/acme-wiki
cd ~/Projects/Acme/acme-wiki
git init
    Or, once the template is on GitHub as a template repo: gh repo create <org>/acme-wiki --private --template <org>/llm-wiki-template --clone
  3. Run /wiki-init in Claude Code inside the wiki folder. It:
    • asks which sibling folders belong to the project and gives each a short prefix (api, web…);
    • reads only the manifests and folder layout to detect each stack, and picks a profile;
    • stops for you to confirm the repos, stacks and profile;
    • fills in the rules, including the never-read list (env files, keys, logs, dumps, customer data);
    • writes the module catalog and the system map;
    • proposes a page plan with a cost estimate, and stops again;
    • builds two pilot pages for you to check, then builds site/.
  4. Check the pilots. Open site/index.html. Read the two pages against the code. If the depth or style is wrong, say so now; it's cheaper than after 50 pages.
  5. Build the rest of the plan with /wiki-build <flow or module>. Main flows first (the journeys the business depends on, and where incidents happen), then one architecture page per app, then the modules with real logic. Pages that don't overlap can be built in parallel by subagents.
  6. Push the wiki to a private repo, and add a short "Developer wiki" section to each code repo's CLAUDE.md (the text is in the template README). From then on, Claude reads the wiki while coding in those repos.
  7. Triage the risk register with the team. Adjust severities in risks.json; expect more risks in older code.

Things specific to existing projects

SituationWhat to do
Docs already in the repos (README, docs/, ADRs)Nothing to copy: pages cite them in place (api:docs/ARCHITECTURE.md). Old docs that disagree with the code get a note.
Docs outside git (Confluence, Google Docs, PDFs, QA reports)Convert to markdown and put them in wiki/raw/. Claude reads them as evidence but never edits them. Remove secrets and customer data first.
Code repos already have a CLAUDE.mdAdd the "Developer wiki" section to the end; keep the rest.
Large legacy system (hundreds of modules)Use the monolith profile. The catalog groups modules by area. Build the 5–10 flows people ask about most; skip modules nobody touches.
Secrets committed in the reposAdd those files to the never-read list during /wiki-init. Rotate them separately; the wiki won't fix that.
Dead codeThe catalog marks modules that look unused, so nobody writes pages for them.

New project

  1. Start once there's a skeleton: the first repo exists and the framework is chosen. /wiki-init works with very little code; the catalog will just be short.
  2. Copy the template and run /wiki-init, exactly as for an existing project (steps 1–3 above).
  3. Write the decisions early. New projects make most of their big choices in the first weeks: the stack, how tenants or users are separated, where money is handled. Ask Claude to record each one as a page in wiki/decisions/, with context and consequences. Put design documents in wiki/raw/.
  4. Draw the system map for the plan, and mark the parts not built yet with > Unverified: planned. Remove the note when the code lands.
  5. Add the code-repo pointer from day one, so Claude uses the wiki while writing the code.
  6. Grow it with each feature. When a feature is merged, run /wiki-build <the feature's flow>. Run /wiki-sync weekly for everything else.
A wiki that starts with the code stays small and accurate, and never needs a big catch-up build.

Any tech stack

The scripts only read markdown and run git diff, so they don't care what language the code is in. Claude reads the code itself. Two files adapt the wiki to your project:

Repo layouts

LayoutHow the wiki handles it
Several repos (API, web, mobile…)One wiki for all of them. Each repo gets a prefix; flow pages follow a request across repos.
MonorepoOne repo, one prefix. The catalog groups modules by app or package.
Single small repoWorks the same; the wiki is just smaller. Consider whether the README is enough.
Mixed stacksFine: each repo is detected separately. The example mixes Next.js, NestJS, Python and Terraform.

The wiki must sit next to the code repos (paths in repos.json are relative, like ../acme-api), so every developer clones them the same way.

Working with Claude

In the wiki folder

CommandWhen
/wiki-initOnce, to set up a new project's wiki
/wiki-build <flow or module>A flow or module has no page yet. Example: /wiki-build password reset
/wiki-syncThe code has new commits. Updates only the affected pages, then rebuilds site/
/wiki-ask <question>Any question. Answers from the wiki, confirms in the code, offers to save the answer
/wiki-lintHealth check: broken citations, stale pages, contradictions, fixed risks

In a code repo

With the "Developer wiki" section in the repo's CLAUDE.md, Claude reads the matching wiki page before changing or explaining code, and checks it against the code. It doesn't edit the wiki from there; it tells you which page a change affects.

Other coding agents

AGENTS.md points other coding agents that read that file to the same rules in CLAUDE.md. The slash commands are Claude Code only, but they're plain markdown you can paste as prompts.

Each project's wiki also gets its own guide page (site/guide.html) written for that project's developers, with its repos and commands. See the example guide.

Keeping it current

  1. Weekly: pull the code repos and run node scripts/wiki-status.mjs. If it says up to date, stop.
  2. Run /wiki-sync in Claude Code. It re-checks only pages that cite changed files.
  3. Review the diff, especially new risks and their ratings in risks.json. Commit and push.
Script (no Claude needed)What it does
node scripts/wiki-status.mjsNew commits per repo, and the pages they affect
node scripts/wiki-lint.mjsEvery citation exists, links work, every page is indexed, stale pages
node scripts/build-site.mjsRebuild everything in site/

FAQ

Does Claude change my code?

No. The wiki rules forbid it. Possible bugs become > Risk: notes for a person to check.

Is my code sent anywhere new?

Claude Code reads the code the same way it does when you use it for coding. Keep the wiki repo private: risk notes describe weaknesses. The never-read list keeps secrets and customer data out of both the prompts and the pages.

What if the wiki is wrong?

The code wins. Each page records the commit it was checked against; /wiki-sync and /wiki-lint find pages that have drifted. Anyone can fix a page, as long as the fix cites the code.

Can I use it without Claude?

Reading, yes: it's plain markdown and HTML. Writing and syncing pages is what Claude does; you can do it by hand, but that's the work the template exists to save.

We already have Confluence / Notion docs. Do we need this?

Those docs are for people and drift from the code. This wiki is checked against the code and kept current by agents. Put useful outside docs into wiki/raw/ as evidence and let the wiki pages cite them.

Can one wiki cover several products?

Use one wiki per product (one set of repos released together). Shared libraries can have their own wiki with the library profile.
